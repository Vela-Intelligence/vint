# Review — September 2026

An assessment of vint at `6d00aa5` (v0.4.1): what it is, where it fits, and
what a full read of the source found. Findings were reproduced by execution,
not by inspection. Those fixed in v0.5.0 are marked; the rest are open and
unscheduled.

This document is written to be read by someone looking for reasons the
project's claims do not hold. Where the evidence is weak, it says so.

## Objective

The stated objective is to maximize *the probability that a model writes a
correct app on the first try, and can diagnose a failure on the second*
([design.md](design.md)). The design follows from it: Solid semantics
inherited rather than invented, so a model's prior is already correct; a
numbered behavioral contract that outranks the code; error messages written
as imperatives; a ~2k-token agent guide shipped as a deliverable.

That objective is coherent and the implementation follows it. Two
qualifications belong next to it.

**The metric is currently near its ceiling.** Across the eval's ten small
tasks, four engines, and five conditions, every arm except VanJS scores
48–50 out of 50. A metric that cannot separate vint from React or Solid on
those tasks also cannot, on that evidence, be said to have *driven* the
design choices it is credited with. The signal that exists is the VanJS gap
and the large-app cell (n=5). See [the eval section](#the-eval-as-evidence).

**The transferable output is a method, not a framework.** Contract-first
change control, agent-artifact alignment enforced in CI, errors written as
prompts, and an eval harness with calibration arms — that package is
reusable independently of vint. The library is the specimen it was
demonstrated on. Positioning vint primarily as a framework invites
comparison on ecosystem, maintainer count, and release maturity, which are
its weakest axes and are not what it is for.

## Position

vint is a ~1,400-line, zero-dependency, single-file library pairing VanJS's
tag-function authoring with a reimplementation of Solid's reactive
scheduler. Its distinguishing artifacts are the contract, the agent guide,
and the error codes — not the runtime.

### The problem it addresses

An agent producing UI into a no-build target — a vendored HTML page, a
generated artifact, an internal tool — has three options today. React
requires a build chain. Solid without its compiler is awkward. VanJS,
Alpine, or hand-written DOM are build-free but carry silent-staleness
failure modes: the app renders, looks right, and is wrong.

The eval measures that third option directly. VanJS scores 22–38/50 pass@1
across four engines with the weakest pass@2 recovery in the set. That is
consistent with the stated diagnosis — silent staleness leaves a model
nothing to work from — though the eval was designed by the same person who
made that diagnosis, so it confirms rather than tests it.

### Where it fits

Reasonable fit when a model writes most of the UI, the target is no-build or
vendored, loud failure is preferred over plausible failure, the app composes
web components, and it stays small-to-medium.

Poor fit when SSR or hydration is needed (explicit non-goals), when routing,
forms, or i18n are needed, when humans are the majority authors and will
want community answers, when lists exceed roughly a thousand rows with
frequent reordering ([F2](#f2), [F3](#f3)), or when the organization
requires an npm-resolvable dependency — there is currently no published
package.

### What the evidence supports

That vint scores comparably to React and Solid on the eval's tasks, on four
engines, from types alone at small sizes and from the guide at larger ones.
It does not yet support a claim that vint is *better* for agent-authored
code than the frameworks models already know; the small-task numbers are
tied at the ceiling, and the one differentiating cell is five samples wide.

### F1

**`mount()`'s disposer leaves DOM behind when the view's top-level child is
a live binding.** Violated D9 and O5. Fixed in 0.5.0.

`mount` snapshotted `fragment.childNodes` before the deferred render effects
ran. Because `createRoot` holds `batchDepth` for the duration of its body,
the snapshot contained only `bindChild`'s two comment markers. On dispose,
cleanups run LIFO and `mount`'s was registered last, so it ran first,
detaching `start`; `bindChild`'s own cleanup then walked from a detached
marker, found nothing, and left the content in place.

```
const d = mount(host, () => Show({ when: on, children: () => div("branch") }))
// post-mount   : [ <!--v-->, <div>branch</div>, <!--/v--> ]
d()
// post-dispose : [ <div>branch</div> ]     ← leaked
```

Affected shapes, all idiomatic: `Show` at top level (a route or auth gate),
a component returning `() => ...`, an array containing a function, a bare
accessor. `For` was unaffected — its rows are separately owned, and
`cleanNode` disposes owned children before running the owner's cleanups.

The existing D9 test missed it because it wrapped the binding in `tags.p()`,
so the snapshot held a real element whose removal took the subtree with it.

Fixed by registering `mount`'s removal cleanup before the view builds, so
LIFO runs it last and each binding clears its own range while its markers
are still attached. D9 now states the guarantee explicitly; four regression
tests cover the affected shapes plus `ShadowRoot`.

### F2

**`For`'s reorder is greedy rather than minimal.** Open.

Step 4 walks target order with a cursor and relocates any row not already in
place. Optimal for appends and adjacent swaps; worst-case when one row moves
past many, because every row it passed is relocated instead.

| Operation on a 100-row list | `insertBefore` calls | Minimum |
|---|---|---|
| Append one row | 2 | 2 |
| Swap two adjacent rows | 2 | 2 |
| Reverse the list | 198 | 198 |
| Move first row to last | 198 | 2 |

This is the same algorithm class as React's `lastPlacedIndex`. Solid's
`mapArray` uses an LIS-style pass and would perform 2. The secondary cost
matters more than the speed: reinserting a node clears its focus, selection,
and IME state, so C2's "focus in unmoved rows survives" holds over a smaller
set of rows than it needs to.

Fix: compute a longest-increasing-subsequence of retained rows and move only
rows outside it. Contained to step 4; C2 needs no rewording.

### F3

**`For`'s reconcile is O(total DOM nodes) per update regardless of what
changed.** Open.

`rowNodes(row)` walks a row's sibling chain, and step 4 calls it for every
row on every reconcile, alongside a fresh key array, `Set`, and `Map` each
pass. Appending one row therefore costs what reordering everything costs.

| List size | Append one row | Update one row's field |
|---|---|---|
| 200 | 0.12 ms | 0.19 ms |
| 1,000 | 0.72 ms | 0.65 ms |
| 3,000 | 4.60 ms | 4.59 ms |

Measured under happy-dom via vitest, so absolute timings are inflated
relative to a browser; the finding is the flat profile across the two
columns and the superlinear growth down them. Below ~500 rows this is not
observable. Past ~2,000 rows a keystroke in a filtered list starts dropping
frames.

Fix: cache each row's node range on the `Row` record, invalidating only when
that row's own binding writes.

### F4

**`E-CALLBACK-PROP` guards only `fn.length > 0`.** Open.

The 0.4.1 warning covers a function *declaring parameters* under a non-event
prop key. Zero-argument callback properties — common in Lit as `renderer`,
`itemTemplate`, or a lazy factory — are still invoked once and their return
assigned, with no warning.

```
div({ formatter: (v) => "x" + v })   // E-CALLBACK-PROP warns
div({ renderer: () => html`...` })   // invoked, assigned, silent
```

Zero-arity is the case where the value alone cannot distinguish a callback
from a binding, so it is the case that most needs a signal. The half already
covered is the half a careful reader could catch unaided.

Fix: on a hyphenated (custom-element) tag name, warn on any function under a
non-event, non-`prop:` key whose assignment target is an existing property.

### F5

**The most likely Solid-transfer mistakes produced raw `TypeError`s.**
Fixed in 0.5.0.

In Solid's JSX, `when` is a value — the compiler wraps it. A model
transferring that prior to vint hit:

```
Show({ when: user() })              TypeError: props.when is not a function
Match({ when: ready() })            TypeError: arms[i].when is not a function
Show({ children: div("x") })        TypeError: props.children is not a function
For({ each: xs, children: li() })   TypeError: props.children is not a function
mount(null, App)                    TypeError: Cannot read properties of null
mount(document, App)                (silently accepted)
```

`For`'s `each` had `E-FOR-ARRAY` for the direct analogue; nothing else did.
Given that "fail loud, instantly, and descriptively" is the second design
principle, this was a gap in the region the design doc identifies as
highest-value.

Fixed with `E-SHOW-WHEN`, `E-MATCH-WHEN`, `E-CHILDREN-FN`, and
`E-MOUNT-CONTAINER`, all always-on. The first two name the Solid divergence
in the message text. `E-MOUNT-CONTAINER` accepts `Element` and
`ShadowRoot`/`DocumentFragment` and rejects `null`, `document`, and selector
strings.

### F6

**`javascript:` URLs passed through unguarded while `innerHTML` warned.**
Fixed in 0.5.0.

D10 listed the untrusted-data sinks correctly; only one was enforced.
`innerHTML`/`outerHTML`/`srcdoc` warned via `E-RAW-HTML`, while `href`,
`src`, and `action` — named in the same clause — were silent. That is the
highest-frequency sink after raw HTML and the one reached for when rendering
a link from API data.

Fixed with `E-URL-SCHEME` (dev warning, still assigns), covering
`javascript:`, `vbscript:`, and non-image `data:` on
`href`/`src`/`action`/`poster`/`formAction`, through both the `prop:` and
`attr:` routings. ASCII control characters are stripped before the scheme is
matched, as browsers do, so `java\tscript:` does not evade it.

This closes the enforcement gap but does not make props safe by
construction, and it is a dev-mode warning only — production code built
through Vite loses it. D10 remains the operative guidance.

### F7

**Contract R10 overstates where a memo's error surfaces.** Open.

R10 says a throwing memo "propagates the error to its reader." When the
reader is an effect, the throw occurs inside `updateIfNecessary` while
validating the effect's sources, before the effect body runs. A `try/catch`
inside the effect never sees it; the error surfaces from the flush.

```
createEffect(() => { try { seen.push(m()) } catch { seen.push("E") } })
setA(1)   // memo throws
setA(2)
// seen === [0, 2] — the catch never ran
```

Behavior is correct and recovery works as promised. This is wording. It
matters because the project's stated rule is that the contract wins and the
code is the bug; leaving the contract imprecise inverts that rule quietly.

Fix: state in R10 that when the reader is a queued computation, the error
surfaces from the flush rather than at the read site.

### F8

**Repeated reads register duplicate observer edges.** Open; matches Solid.

A signal read *n* times inside one computation registers *n* edges — 1,000
reads produced 1,000 observers. Each subsequent write walks all of them.
Solid 1.x behaves identically, so this is not a divergence from an inherited
prior and requires no contract change. It is worth knowing because a memo
reading a signal inside a `reduce` over a large list allocates
proportionally on every run.

### F9

**Prose error-code counts drifted from `src/dev.ts`.** Fixed in 0.5.0.

README.md and design.md both stated "Nineteen error codes" against 21
defined. `check-alignment.mjs` verified that every code appears in
llms.txt, SKILL.md, and contract.md, and that none of those names a code
that does not exist — but it did not read prose counts, and did not check
design.md at all. The guard reported green while the two most-read documents
were wrong.

Fixed by correcting both counts and extending the alignment script to assert
the spelled-out count against the number of codes defined. The guard was
verified to fail on reintroduced drift.

### F10

**The `tags` proxy answers every string key.** Open; cosmetic.

`typeof tags.then === "function"`, making `tags` a thenable, so awaiting
anything that resolves to it hangs. `String(tags)` and template
interpolation throw "Cannot convert object to primitive value" for the same
reason. Neither is a shape a model is likely to produce. Both are one
denylist entry (`then`, `toString`, `valueOf`, `Symbol.toPrimitive`) away
from being impossible.

## Security

All of the following was verified by execution.

Holding:

- **Children are XSS-safe by construction.** `<img src=x onerror=alert(1)>`
  as a child renders as escaped text; no string in the children path is
  parsed as HTML.
- **Prototype pollution is blocked.** A `JSON.parse`-derived `__proto__` key
  is dropped with `E-PROTO-KEY`; `Object.prototype` was unmodified.
- **Attacker-shaped spreads degrade safely.** `{"onclick": "alert(1)"}` is
  skipped with `E-EVENT-VALUE` rather than reaching a live `onclick`
  attribute.
- **Supply chain is small and pinned.** Zero runtime dependencies, six dev
  dependencies, no install scripts. CI actions are pinned to full commit
  SHAs under `permissions: contents: read`; the release job scopes write
  separately. `dist/` is gitignored and built at tag time; a rebuild
  reproduced the released bundle byte-identically.

Remaining gaps:

- **Props are not safe by construction, and the guards are dev-mode only.**
  `E-RAW-HTML` and `E-URL-SCHEME` both warn and proceed, and both are
  compiled out of a Vite production build. They shorten a debugging loop;
  they are not a control.
- **Computed tag names** construct `script` elements, including under
  `tagsNS` in the SVG namespace. The proxy cannot distinguish a literal key
  from a data-derived one, so documentation is arguably the only available
  answer — but D10 should say that explicitly rather than leaving it looking
  like an oversight.
- **No CSP guidance.** The documented happy path is a vendored file dropped
  into a page with no build step, which is the deployment where CSP is the
  primary defense and where the author has no bundler to lean on.

## The eval as evidence

The harness ([eval/README.md](../eval/README.md)) is well constructed as
internal engineering: reference-solution calibration arms that prove the
pipeline passable without API calls, a controlled A/B on the `For`
divergence, per-run cost accounting, refusals recorded and excluded, and an
incident log covering biases found and corrected — including a
safety-classifier refusal that was condition-biased, which is a validity
hazard most evals do not detect.

As a public claim it has four weaknesses, all fixable.

| Issue | Detail | Effect |
|---|---|---|
| Unequal denominators | `vint-bare` reports 64/65 for Terra and Luna against /50 elsewhere in the same table; `summary.mjs` folds the A/B run's 10-sample cells on tasks 02/05/10 into the row. | A table read as like-for-like over-weights three tasks in one condition. |
| Ceiling effect | Outside VanJS, nearly every cell is 48–50/50. | The metric cannot discriminate among the design choices it is credited with driving. |
| n = 5, no intervals | The large-app table's 3/5 vs 5/5 differences are twenty binomial trials, reported without confidence intervals. | "The only condition of five reaching 5/5 on all four engines" is a statement about coin flips. |
| Asymmetric calibration | Reference solutions exist for 11 vint tasks but 1 React, 2 Solid, 2 VanJS. | The arm's stated purpose — proving acceptance tests passable — is established for vint and spot-checked for baselines. |

Beneath all four: the framework, the guide, the task specs, and the
acceptance tests share one author. The eval README is candid about specific
biases it caught, which is worth credit, but self-authored acceptance
criteria are the one threat to validity that candor cannot retire. The
strongest available correction is an arm whose tasks and acceptance tests
are written by someone else.

## Open work

Ordered by value per unit of effort.

1. **F2 + F3 — make `For` optimal for reorder and incremental for update.**
   LIS-based placement plus a cached per-row node range turns the two worst
   cases into the two best, and makes C2's focus guarantee hold for every
   row that does not need to move. Roughly two days.
2. **Decide the distribution question.** `package.json` is `private: true`
   with `main: src/index.ts`; the README says "add the repo as a
   dependency"; SKILL.md says "there is no npm package". Three artifacts,
   three answers. The design doc's non-goal is *npm-first* distribution —
   a statement about defaults, not a reason to be uninstallable. Publishing
   the built ESM and `.d.ts` while keeping vendoring as the documented path
   removes the largest adoption barrier for one workflow step.
3. **Give the eval a defensible presentation.** Equal denominators,
   confidence intervals, a task list fixed before results are seen,
   reference solutions for the baselines, and an externally authored arm.
4. **F4 — widen `E-CALLBACK-PROP` to zero-arity on custom elements.**
5. **Ship the verification loop design.md promises.** Principle 3 names "a
   zero-config test harness, because an agent's verification loop is its QA
   department." One exists for the eval, not for users. A small
   `vint/testing` surface — mount into a DOM, settle the flush, assert,
   dispose — would let an agent close the loop on the app it just wrote.
   The principle is currently stated but undelivered.
6. **F7 — correct R10's wording.**
7. **Run a second-implementer test.** Have someone who did not write vint
   build something non-trivial from llms.txt alone and log every point where
   they had to read the source. The guide's sufficiency has been tested
   against models whose priors it was tuned against; it has not been tested
   against a reader who can report what was missing.
